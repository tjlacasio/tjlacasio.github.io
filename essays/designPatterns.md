<br>
	I consider design patterns to be the "house rules" of programming; they don't tell you precisely what to build, but instead offer practical ways to arrange things so the house doesn't fall apart later. Design patterns are reusable solutions to common software design challenges. They offer names and structure to concepts that many developers came up with separately, such as how to manage a single shared resource rather than continually creating it, how to separate data from UI, and how to share layout between pages. Patterns assist in avoiding starting from scratch and make it simpler for other developers to know what you did and why.
<br>
  Even though we didn't initially identify them by name, many of these patterns appear in the RIBows final project, a Next.js application for investigating UH RIOs. One apparent example is a **Layout pattern**: we have a shared layout component that surrounds pages with the same navbar, footer, and theme tokens. We have a single "shell" that all the various views link into, rather than each page creating its own header. Another pattern is a form of **Model–View separation** such as React components render the "view," while Prisma schemas and database queries serve as the "model" layer. When a user loads the RIO list page, the UI doesn’t know the specifics of SQL; it only receives data generated by our model functions and displays cards.
<br>
We also rely on state and access trends. Our use of NextAuth works like a Facade over authentication, rather than hand-writing login processes, token checks, and session storage. We call a API that hides the ugly details but provides a consistent mechanism for checking sessions and protecting sites. Lastly, we use React Hook Form and shared components to reuse a form-handling pattern across our form pages. This ensures that adding or amending a new RIO follows the same structure: validate inputs, display errors, submit to an API route, and then redirect. By the end of this project, “design patterns” ceased sounding like abstract textbook language and started feeling like the subtle guidelines that made our code more predictable, readable, and easier to extend.
